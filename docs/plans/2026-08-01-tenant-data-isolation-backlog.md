# 多账号租户数据隔离安全债务

> 状态：P0 上线阻断（尚未实施）
> 记录日期：2026-08-01 | 审计更新：2026-08-02
> 处理顺序：阶段 02 验收后、业务化多用户 UI 前，按独立 Tenant Isolation Gate 实施

## 已确认的问题

当前系统的登录账号只用于接口鉴权，还不是完整的租户边界。新注册账号登录后，仍可能读取
其他账号已创建的抖音/TikTok 登录账号、客户数据、Pipeline 任务和 LLM 配置。这属于数据
越权风险，不能按普通界面缺陷处理。

## 已识别的影响范围

- 社媒账号及其浏览器 Profile、登录状态、展示名称和头像
- 客户数据库、筛选结果、标签和人工复核状态
- Pipeline 任务、运行记录、调度结果和报告
- LLM Provider、业务路由、调用记录与用量统计
- 后续关键词库、知识库和经验反馈数据

## 后续实施原则

1. 以现有 `accounts.id` 作为 `owner_account_id`，JWT/服务端 Principal 使用不可变账号主键，
   不能只依赖用户名进行过滤。
2. 所有受保护 API 必须先鉴权，再从服务端登录态取得租户身份；禁止信任客户端提交的
   `tenant_id`。
3. 上述业务表补充租户归属和必要的复合唯一约束，所有查询、更新和删除默认强制带租户条件。
4. 社媒浏览器 Profile、Cookie、storage state 和导出文件路径也必须按租户隔离，不能只隔离
   数据库行。
5. 管理员跨租户能力必须采用独立角色和显式审计，普通账号默认不可跨租户读取。
6. 迁移前先定义现有历史数据归属；无法确认归属的数据进入管理员待认领区，不自动暴露给
   新注册用户。

## 2026-08-02 只读安全审计结论

影响范围不止获客接口：客户库、Pipeline Job/Schedule、社媒账号与浏览器 Profile、报告、
事件/SSE、Chroma 向量、LLM Provider/Route/Secret 及配置均存在全局读取或仅登录不验归属
的路径。在完成紧急封口前，不应把服务暴露给多个互不信任的普通账号。

实施拆为五个子门：

1. **T1 紧急封口**：服务端 Principal、业务 API 默认登录、根表 owner、`owner=NULL`
   fail closed，临时关闭尚未隔离的管理入口；
2. **T2 社媒账号与任务**：账号、Profile/storage state、登录会话、Job、Schedule、调度和
   自动选账号全部按 owner 隔离；
3. **T3 客户与六阶段产物**：User、Acquisition、Review、Strategy、Message、Reply、
   Report、Event/SSE 和 Chroma metadata 隔离；
4. **T4 LLM 与配置**：Provider/Route/Usage 按 owner，租户 Secret Store，system config
   与 tenant config 分离；
5. **T5 历史认领与约束强化**：显式管理员认领、冲突拆分、报告重算、向量重建、Profile
   搬迁、复合唯一约束和迁移回滚演练。

旧数据迁移先增加可空 owner，但普通查询立即排除 `owner=NULL`；不得自动把旧数据归给新
注册用户或第一位管理员。无法确认归属的 LLM Secret、日志、向量和报告保持隔离归档。

## 独立验收门槛

- 使用两个普通账号分别创建社媒账号、客户、任务和 LLM 配置，双方列表与详情均不可互见。
- 通过猜测或复用资源 ID 访问另一租户时稳定返回 404 或 403，且不泄露资源是否存在。
- 所有相关 API 均具备未登录 401、跨租户拒绝、同租户正常访问的自动化测试。
- 浏览器 Profile、Cookie、日志、报告和导出文件完成同等隔离验证。
- 迁移脚本可回滚，并在备份数据库副本上完成一次演练后再处理真实数据。

本文件只记录安全债务和验收边界，不代表租户隔离已经实现。
