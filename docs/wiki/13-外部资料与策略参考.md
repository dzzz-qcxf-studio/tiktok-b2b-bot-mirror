**当前项目实现的安全措施** ✅：
- Playwright 默认 `--disable-blink-features=AutomationControlled`
- 评论间隔 3-10 分钟（随机）
- 私信间隔 5-15 分钟（随机）
- 30% 概率穿插浏览 ForYou 页面

**建议补强**（Phase 7+ 优化）：
- 安装 `playwright-stealth` 插件绕过 webdriver 检测
- 引入更多设备指纹伪装（Canvas/WebGL 噪声）

## 9. MediaCrawler 架构研究笔记

> 研究日期: 2026-07-19 | 参考版本: MediaCrawler main (commit depth 1)
> 仓库: https://github.com/NanmiCoder/MediaCrawler
> 关联: [架构设计](02-架构设计.md) | [账号管理](10-账号管理.md)

### 9.1 总体架构

MediaCrawler 是一个多平台社交媒体爬虫框架，以抖音/小红书/微博等为目标。它的架构核心：

```text
main.py
├── config/          # 平台配置（dy_config.py, xhs_config.py ...）
├── base/            # 抽象基类 (AbstractCrawler, AbstractLogin)
├── media_platform/  # 平台实现（douyin/, xhs/, weibo/ ...）
│   ├── login.py     # 登录状态机（QR/手机号/Cookie）
│   ├── core.py      # 核心爬取逻辑（搜索、列表、评论）
│   ├── client.py    # HTTP 客户端 + 签名 + 接口封装
│   └── field.py     # 数据模型/字段定义
├── cache/           # 缓存抽象（Redis / Memory）
├── proxy/           # 代理池
├── database/        # 存储层（异步 SQLite/MySQL）
└── libs/            # 工具库（滑块识别、Cookie 工具等）
```

### 9.2 登录流程（DouYinLogin）

MediaCrawler 的抖音登录实现了 3 种方式的抽象：

```
begin()
├── popup_login_dialog()     → 检查登录框是否自动弹出，否则手动点"登录"按钮
├── login_by_qrcode()        → 从 DOM 抓取二维码 base64 → 显示终端 → 等待扫码
│   └── find_login_qrcode()  → 定位 #animate_qrcode_container img → 取 src
├── login_by_mobile()        → 验证码登录（需配合短信缓存 redis）
│   └── check_page_display_slider() → 滑块验证（边缘检测 + 轨迹模拟）
├── login_by_cookies()       → 从已有 cookie_str 注入 browser_context
└── check_login_state()      → 轮询 localStorage + cookies (LOGIN_STATUS=1)
    └── 重试装饰器 @retry(stop=600, wait=1) → 10分钟超时
```

**关键设计点：**
- `check_login_state()` 使用 `@retry` 装饰器（tenacity）以 1s 间隔轮询 600 次
- QR 码通过 DOM 提取 `base64` 数据，而非截图 OCR
- 滑块验证用边缘检测 `Slide.discern()` 识别缺口位置 + `get_tracks()` 生成仿人轨迹

### 9.3 Client 层（HTTP 通信）

`core.py` 和 `client.py` 构成双层结构：

```text
core.py (业务逻辑层)          → 调 client.py 发请求
├── search_keyword()          → 搜索关键词
├── get_note_list()           → 获取作品列表
├── get_note_comments()       → 获取评论
└── ...

client.py (HTTP 通信层)       → 封装签名 + Cookie + 重试
├── _request()                → 基础请求（UA/Cookie 注入）
├── _pre_handler()            → 签名预处理
└── 签名算法 (X-Bogus / X-Sec-Token 等)
```

**我们的采用策略：**
- 只用其**架构模式**（状态机、分层抽象、重试策略）
- **不照搬签名算法**（X-Bogus 等属于逆向工程，违反项目边界）
- QR 登录流程改为：用户在真实浏览器完成扫码 → 服务端只拿 cookie

### 9.4 对我们项目的影响

| MediaCrawler 做法 | 我们的处理 | 理由 |
|---|---|---|
| 二维码从 DOM 抓 base64 | ❌ 不用。用户自己用手机扫真正的二维码 | 避免逆向 DOM 结构 |
| 滑块验证自动通过 | ❌ 跳过。如遇滑块，降级为人工处理 | 滑块验证属 detection evasion |
| `@retry` 轮询登录态 | ✅ 借鉴。用 tenacity 或 setInterval 轮询 cookie | 纯逻辑，不涉及反爬 |
| `BrowserContext` 管理 cookie | ✅ 借鉴。我们的 AccountSession 也基于 Playwright context | 标准 Playwright 用法 |
| 签名算法内联在 client | ❌ 不用。无签名，只做公开搜索 | 合规边界 |
| 平台配置独立（dy_config.py） | ✅ 借鉴。我们的 ConfigAccounts 已按平台分离 | 工程最佳实践 |
