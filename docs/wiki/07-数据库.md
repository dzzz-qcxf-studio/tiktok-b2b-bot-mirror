### tiktok_accounts（社交平台账号）

| 列 | 类型 | 说明 |
| --- | --- | --- |
| id | PK | 主键 |
| platform | VARCHAR(20) | tiktok / douyin |
| username | TEXT | 浏览器隔离 alias（如 marketing_01），登录后不直接改名 |
| display_name | VARCHAR(100) | 用户可编辑的本地展示备注；空值回退平台昵称 |
| nickname | TEXT | 平台昵称 |
| avatar_url | VARCHAR(1000) | 已验证平台资料中的 HTTPS 头像 URL |
| cookies_json | TEXT | Playwright cookies 序列化 JSON |
| status | TEXT | pending / logged_in / expired |
| login_method | TEXT | qrcode / phone / password |
| qrcode_token | TEXT | 当前登录会话 token |
| last_login_at | DATETIME | 上次登录时间 |
| follower_count | INTEGER | 账号粉丝数 |
| browser_provider | VARCHAR(50) | Provider 标识；TikTok 未配置时为空 |
| browser_profile_id | VARCHAR(200) | 指纹浏览器 Profile 标识 |
| created_at | DATETIME | 创建时间 |
| updated_at | DATETIME | 更新时间 |

唯一约束：`(platform, username)` — 同名账号在不同平台可独立存在

`username` 写入前统一执行 Unicode NFKC 与首尾空白清理并保留大小写。由于物理唯一
约束只比较规范化后存入的文本，新增账号与首次登录入库会先执行 SQLite
`BEGIN IMMEDIATE`，再在同一事务中扫描同平台全部 alias、检查账号上限并插入；这使
多进程并发的 `A`/`Ａ` 或 `foo`/` foo ` 不会形成两条逻辑重复记录。历史库若已经存在
多条规范化等价 alias，resolver 返回 `account_alias_conflict` 而不任取一条。

账号上限是跨平台全局 `MAX_ACCOUNTS`。零匹配的新登录 alias 会先做只读容量预检，避免
无意义地打开浏览器；首次登录 updater 仍在 `BEGIN IMMEDIATE` 后按“alias 冲突扫描 →
全局账号 count → insert”的顺序执行权威检查。已有账号只更新原行，不受满额阻止；
并发争夺最后名额时第二个事务在看到最新 count 后返回 `account_limit_reached`。

`display_name` 与 `username` 分离：前者只影响 UI 展示，后者参与唯一约束、账号解析、
Profile 和 storage state 隔离路径，不能用普通备注编辑接口改写。`display_name` 与
`avatar_url` 都带空字符串服务端默认值，旧 SQLite 数据库启动时可通过轻量迁移安全补列，
不会重建或清空既有账号表。

### llm_providers

保存 UUID、唯一 `name`、显示名、固定协议 `openai_chat`、`base_url`、
`default_model`、`api_key_env`、启停状态、超时和时间戳。`api_key_env` 必须匹配
`[A-Z][A-Z0-9_]*`；表中不存在 API Key 明文字段。

### llm_routes

每行是一个业务 Route 的一个 Provider 条目，保存 `route_key/provider_id/priority/
model_override/enabled`，并对 `(route_key, provider_id)` 建唯一约束。合法 Route 固定为
`collection / qualification / strategy / iteration / default`。完整链条由
`LLMStore.replace_route_chain()` 在同一事务中校验后替换；Provider 仍被引用时禁止删除。
Provider/Route 写事务先取得 SQLite `BEGIN IMMEDIATE` 保留锁，避免“验证存在后另一事务
删除”的 TOCTOU；同名 Provider 竞争稳定映射为业务冲突。
普通 SELECT 造成的 SQLAlchemy 逻辑 autobegin 不会跳过该锁；若底层 SQLite 已存在
不受 `LLMStore` 管理的真实事务，写入会返回明确事务错误，要求调用方使用新的或受管理的
Session，而不是退化成 DEFERRED check-then-write。

### llm_request_logs

保存 route、Provider 快照、模型、成功/失败、错误分类、input/output/total tokens、
延迟、是否 fallback 和时间。表中不保存 prompt、response、API Key 或完整上游错误正文；
Provider 删除后日志仍保留，`provider_id` 可置空而 `provider_name` 快照继续用于审计。

### 获客阶段 01/02 表

- `acquisition_campaigns`：每个 Job 最多一行，保存平台、国家/语言/行业/产品、硬性与
  偏好条件、排除目标、七项搜索预算和 effective/new 关键词比例；创建后不可变。
- `acquisition_keywords`：Job 内关键词、语言、类型、来源、状态，以及 usage/video/
  relevant_video/candidate/qualified/reply/business_lead 计数和最后使用时间。
- `discovery_evidence`：以 `job_id + user_id` 归属候选，保存关键词、视频、评论、作者
  URL、原文/翻译、相关度、完整度和只含公开来源路径的 metadata。Service 在
  `BEGIN IMMEDIATE` 下用稳定来源指纹去重，相同重试不复制，不同来源仍分别保留。
- `candidate_assessments`：AI 多标签、匹配度、可信度、正/负证据、缺失字段、推理、
  建议状态、模型和 Schema 版本；只追加不覆盖人工结论。
- `candidate_review_audits`：人工动作、前后状态/标签、操作人、原因和版本；
  `review_version` 用于并发写入冲突检测。

`pipeline_job_users` 同时保留 legacy `status` 和新的 `discovery_status /
qualification_status / match_score / confidence_score / labels_json / missing_fields_json /
review_version`。数据库触发器仅做兼容状态同步，AI 标签和人工标签分别保存。

AI 资格更新必须同时匹配 `job_id + user_id + review_version + 起始 qualification_status`，
并要求 `manually_confirmed_at IS NULL`。该内部更新入口拒绝 `qualified` 和 `rejected`；
只有带人工审计的状态迁移能够写入两个终态。AI 评估继续追加到
`candidate_assessments`，但 CAS 失败时不得反写
`pipeline_job_users` 的当前双评分、标签或资格状态。

阶段 02 与阶段 03 使用 `user_id` keyset 分页，避免固定 `LIMIT 200/100` 造成后续候选永久
饥饿。阶段 04 读取 Campaign 策略时再次校验当前 Job、平台、人工合格状态和严格策略契约。

### pipeline_job_stages

每个 Job 的阶段明细，`(job_id, stage)` 唯一。保存 `stage_order/status/attempt/
result_json/error_message/started_at/finished_at`，支持阶段级恢复与重试。

### pipeline_schedules

统一定时计划。保存 `name/platform/account_mode/account_id/stages_json`、
五段 `cron_expression`、`timezone/enabled/config_json` 和
`next_run_at/last_run_at`。Scheduler 到期后仍向 `pipeline_jobs` 写普通 Job，
不会建立第二套历史。

### pipeline_job_users

Job 与用户的复合主键关联，保存 `source_stage/status/category` 和时间戳。
筛选、策略、触达、报告和迭代按此表隔离，避免一个平台或任务污染另一个任务状态。

`strategies.job_id`、`messages.job_id` 与 `experience_rules.job_id/platform`
继续把后续产物归属到具体任务。消息在外部发送前先写 `sending` 预留；
异常后记录 `uncertain`，相同 Job 不会自动再次发送。

## 状态与一致性

- Job：`queued/running/cancelling/cancelled/succeeded/partial_failed/failed/interrupted`
- Stage：`pending/running/succeeded/failed/skipped/cancelled`
- 认领、取消和状态迁移使用带期望状态的条件 UPDATE，SQLite 是队列权威源。
- 服务启动将遗留 running Stage 标为 failed，并将 Job 标为 interrupted。
- 重试创建新 Job 并指向 `retry_of_job_id`，不篡改原任务审计记录。legacy Job 从首个失败
  阶段继续；AI 获客 Job 从 `collect` 继续，并以一个事务复制 Campaign/关键词定义。

### Hermes H1 事务边界与只读投影

- `POST /api/acquisition/jobs` 在事务外完成账号/Provider 预检，在同一事务写入
  `pipeline_jobs`、`pipeline_job_stages`、`acquisition_campaigns` 和全部初始
  `acquisition_keywords`。只有提交后 queued Job 才能被另一连接和 Dispatcher 看到。
- 在进入事务前，API 与 Service 都要求阶段为六阶段的严格有序子序列且包含 `collect`，并
  递归拒绝 `config_snapshot_json` 中的凭据类键及缩写/结构化认证载荷；因此倒序阶段和敏感
  配置不会落库或被后续 API 回显。
- AI retry 在同一事务创建新 Job 并复制 Campaign 与关键词定义；不复制 Evidence、
  Assessment、Review Audit，且 usage/video/candidate/business-lead 等运行计数使用新行默认
  值 0，避免把上次部分执行误当成本次结果。
- `BusinessReadModel` 不新增权威表。它对每个 User 只选择存在 Campaign 的最新
  `PipelineJobUser`（`PipelineJob.created_at DESC, PipelineJob.id DESC`），再投影资格、分类、
  双评分、标签和来源 Job；`User.status/category` 保持不变。
- AI 关键词总候选数按同 Job Evidence 中不同用户实时统计，合格数按同 Job 的
  `qualification_status=qualified` 统计；legacy 关键词按 `User.source=keyword_search` 聚合。
  同名关键词跨两类来源按不同用户合并，不读取可能过期的 `AcquisitionKeyword` 计数列。
- 报告漏斗使用累计投影；地区和情感来自真实 Message/Reply；商业意向按已发送消息对应的
  不同 Reply 用户统计。“今日”字段以 UTC 00:00 为边界。

## Schema 迁移

`Database.init()` 走 `Base.metadata.create_all(engine)`，创建缺失表。
**新增列**用 `database.py:_migrate()` 幂等补齐:

- 用 `PRAGMA table_info` 查现有列
- 对迁移清单中的 ORM 简单列执行 `ALTER TABLE ADD COLUMN`
- 对非空默认列同时写入 SQLite server default，兼容已有数据
- 补建 `job_id`、Provider/Profile 等索引
- 已存在的列跳过

三张 LLM 表由 metadata 创建。建表和列迁移完成后，如果 Provider 表为空，
`seed_legacy_llm_config()` 会先执行 `BEGIN IMMEDIATE`，再在单个事务中创建
`legacy-default` 与五条 Route；并发或重复启动不会重复插入，也不会复制
`Settings.llm_api_key` 的值。

每个 SQLite 连接都执行 `PRAGMA foreign_keys=ON` 与 30 秒 busy timeout，确保
`RESTRICT/SET NULL` 不是只写在 ORM 声明里的“纸面约束”。Provider、Route、用量字段还
有数据库 CHECK 兜底；应用层会更早拒绝字符串布尔值、浮点 priority、NaN/Infinity 和
负数 Token/延迟。

> 生产环境建议改用 Alembic;此处仅为开发期补缺,避免手动 DROP / 重灌库。

迁移 `new_today` 字段使用 `created_at >= date.today()` 做 UTC 当日分界
(SQLite 存的 datetime 是 naive UTC,与 ORM `datetime.utcnow()` 一致)。
