## 依赖方向

```
UI (Vue) ──http──▶ API (FastAPI) ──create──▶ PipelineJobService
CLI (Click) ────────────────create──────────▶ PipelineJobService
Skills (Hermes) ──CLI──▶ CLI ──call──▶ Core
Scheduler ──────────────create──────────────▶ PipelineJobService
                              │
                              ▼
                   SQLite Job/Stage/Schedule
                              │
                              ▼
                 Dispatcher → Runner → Provider → Plugin
```

**核心原则：**
- UI 不直接调 Core
- API、CLI、Scheduler 都通过 `PipelineJobService` 创建同一种持久化任务
- SQLite 是任务队列和状态的唯一权威源，不维护第二套内存任务系统
- Skills 是 CLI 的 Hermes 包装
- 平台差异只在 `Platform` 与 `BrowserProvider` 边界内处理

## 统一运行时

FastAPI lifespan 启动一个 `PipelineRuntime`。它先把上次进程遗留的
`running/cancelling` 任务恢复为 `interrupted`，再启动 Scheduler 与 Dispatcher：

1. Scheduler 根据 `pipeline_schedules.next_run_at` 创建 `trigger_type=schedule` 的 Job；
2. Dispatcher 只从 `pipeline_jobs.status=queued` 认领任务；
3. Runner 按顺序持久化每个 Stage，并在阶段边界响应取消；
4. `auto` 模式在账号忙时保留 queued，`specified` 模式只使用指定的同平台账号；
5. 重试创建 `trigger_type=retry` 且带 `retry_of_job_id` 的新 Job，从首个失败阶段继续。

当前合法触发来源为 `manual/schedule/retry/legacy`。

### Hermes H1 原子建单与统一读模型

Hermes 不建立第二套任务系统。AI 获客通过受认证的 `POST /api/acquisition/jobs` 进入现有
Pipeline 队列：`AcquisitionJobService` 先在事务外完成账号与 Browser Provider 预检，再在
同一数据库事务中创建 `PipelineJob`、全部 `PipelineJobStage`、`AcquisitionCampaign` 和
1—100 个 `AcquisitionKeyword`。只有整个事务提交后，Dispatcher 才能看到 queued Job；
任一写入失败都会整体回滚。

创建前，API 与 Service 共用两道不可绕过的输入闸门：阶段列表必须包含 `collect` 且是六阶段
定义的严格有序子序列；开放的 `configSnapshot` 会递归拒绝凭据类键、常见 `auth` 缩写和
Bearer/Basic/OAuth 认证结构，且错误不回显原始键值。

```text
Pipeline / Hermes
       │
       ▼
AcquisitionJobService ──同一事务──▶ Job + Campaign + Keywords
       │
       ▼
Pipeline Dispatcher / Runner
       │
       ▼
Job 级 Evidence / Assessment / Review
       │
       ▼
BusinessReadModel ──▶ Users / Lead / Dashboard / Reports / Wordcloud
```

`User` 仍只负责平台身份和公开资料。某次获客任务的资格状态、分类、评分、标签和证据保留
在 Job 级表中；全局页面由 `BusinessReadModel` 选择最新 Campaign Job 并投影，绝不为了
兼容旧页面而覆盖 `User.status/category`。状态展示优先级为：真实 Reply、已发送 Message、
最新 AI 资格（`qualified/rejected`）、AI 待处理映射为 `pending`，最后才回退 legacy User。

带 Campaign 的 retry Job 从 `collect` 重新开始，并在一次事务中克隆 Campaign 和关键词
定义；本次执行计数清零。没有 Campaign 的 legacy Job 仍从首个失败阶段继续。

抖音任务由 `DouyinPlaywrightProvider` 为每次执行创建独立浏览器 Context。
TikTok 默认注册不可用的指纹 Provider 占位实现；未接入具体厂商前会阻止任务创建，
不会用抖音的 Playwright Provider 兜底。

## LLM 配置权威源

`Database.init()` 创建 LLM 三表，并且只在 Provider 表为空时把 legacy Settings 映射为
`legacy-default` Provider 和五条默认业务 Route。数据库只保存 `api_key_env`，不保存
密钥值；`LLMStore` 负责 Provider CRUD、Route 链原子替换和不含 prompt/response 的
用量日志。

`LLMRouter` 在每次请求时读取已启用 Route 链，按优先级最多尝试三家 Provider。
HTTP 408/429/500/502/503/504、超时和网络故障允许切换备用；鉴权、请求参数、
本地配置、其他已识别 HTTP 状态和 JSON 解析失败立即停止。Provider 连续三次可重试
失败后进入 Open，60 秒后只允许一个 Half Open 探针；探针失败或取消会重新 Open 并
释放占用。OpenAI-compatible 适配器每次从
`api_key_env` 指向的环境变量读取密钥；配置或密钥变化时刷新 SDK Client。
SDK 的隐式重试固定为 0，只有 Router 能决定 fallback 次数。Route 读取和用量写入通过
工作线程各自创建、使用和关闭数据库 Session；用量元数据先进入有界后台队列，写入失败
或队列满只增加安全计数，不延迟或改变 Provider fallback、熔断和业务结果。熔断 lease
带 generation，旧并发请求不能篡改新 Half Open 探针。
被删除 Provider、轮换后的旧 Client 和 API shutdown 都会等待在途请求后确定性关闭。
删除 Provider 的关闭任务不在其他 Route 的请求路径等待，只由后台任务与 Router
shutdown 跟踪；旧 Client 的在途请求不会拖住无关业务 Route。
`get_llm_client()` 只是同一 Router 的迁移 facade，不保留第二套执行逻辑。
